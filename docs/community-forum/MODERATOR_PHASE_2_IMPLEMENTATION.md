## What was built
**Schema** (additive; both Prisma schemas, MariaDB migration validated, PostgreSQL copy written but NOT executed): `UserRole.COMMUNITY_MODERATOR`; `User.linkedCustomerId` (unique FK to Customer); `ModeratorAppointment`, `ModeratorAppointmentEvent`, `MemberWarning`, `MemberRestriction`, `ModerationAppeal`, `ModerationEscalation`. No column drops or data changes. Rollback: after rolling the code back, drop the six new tables and `User.linkedCustomerId`; the enum value can stay unused.

**Permissions** (`src/server/auth/permissions.ts`): moderator holds exactly nine `mod:*` capabilities (queue read, post review, comment moderate, report handle, submission review, member warn, member restrict (max 7 days), own history, sensitive hide). Administrators gain those plus `mod:appoint`, `mod:appeal:decide`, `mod:restriction:manage`, `mod:escalation:read`. Moderators have none of: deals, accounts, security, merchant, category, affiliate, operations/analytics, audit, `forum:moderate`, `forum:manage`, community settings, announcements. Existing broad gates were **not widened**: `moderation.ts` services now check the specific `mod:*` capability instead of `forum:moderate`; administrators hold both, so their behaviour is unchanged (9/9 existing community-forum tests pass). Private-message reports, member suspension, community settings, verified badges stay admin-only.

**Appointment** (`moderators.ts`): admin invites an existing member; single-use token, 7 days, HMAC-hashed in the database; only the invited, signed-in customer can open or accept it; guideline consent (versioned) is mandatory; acceptance is one conditional update (race-safe); a staff account is then created in the existing PENDING_SETUP state and bound to **that customer's id** (email equality is never used); password and authenticator are set up through the existing staff setup flow (real TOTP verified in tests). Probation is 30 days, never auto-confirms: administrators confirm (only after the period ends), extend (7-30 days with a reason, at most twice) or revoke. If probation ends with no decision, **moderator access pauses** (it is not confirmation). Revocation suspends the staff account, deletes every staff session and open setup link at once, keeps all history. Generic account tools cannot create, promote, demote, suspend or reactivate a moderator. A previously revoked moderator can be re-appointed with a fresh password and authenticator.

**Access** (`moderator-access.ts`): every moderator API call re-checks account active + authenticator + customer binding + appointment in force. `adminApi` and the admin layout reject moderators. Separate surfaces: `/moderator` (dashboard) and `/api/v1/moderator/*`.

**Moderation** (`discipline.ts`, `moderation.ts`, `review.ts`): post/comment actions (existing version-checked transactions, history + audit in one transaction), reports (reporter identity hidden from moderators), community deal review where approval creates only a plain DRAFT (`saveDeal` has a draft-only path that refuses editing, any other status, affiliate data, options or featured flags; publishing still needs `deal:publish`), and moderators see only a submitter's user name, not their email or real name. Warnings (private, reason shown, moderator never named). Posting restrictions: 1-7 days for moderators (admins up to 30), one active at a time, at most two per member per month, 10 per hour; enforced by the clock in `createPost`, `editPost`, `createComment` (also replies), `editComment` and community deal submissions/resubmissions; reading, votes, saves, deleting own content and private messages stay available; `ForumProfile.status` is never touched. Appeals against restrictions, warnings and removals: one per target, decided only by an administrator who did not take the action; overturning undoes the action (lifts the restriction, withdraws the warning, restores the content). Sensitive content: one transaction hides it, writes history + audit with no content, and creates a redacted escalation; only an administrator can open the hidden item and that access is audited. Moderators cannot re-read it.

**Screens**: `/moderator` (queue, reports, community deals, warn/restrict, my history; responsive); `/admin/moderators` (invite, probation decisions, appeals, hidden content, running restrictions; added to the admin navigation); `/community/moderator-invite` (guidelines and acceptance); `/community/moderation` (member's notices and appeals); notification types for warnings, restrictions and appeal decisions.

## Gates and limitations
- **Owner decision needed:** apply `20261126100000_community_moderator` to the persistent local database (and later staging). Until then the moderator screens fail on the running dev server.
- Probation that ends with no decision **pauses** access rather than continuing it; flagged as "decision due" for administrators.
- The invitation link is shown once to the administrator for hand delivery; no email is sent (no mail path was added).
- Moderators cannot read hidden/sensitive content after hiding it; evidence is only the non-public record, opened by administrators with an audit entry. Image evidence is not exposed anywhere (the existing image route already refuses non-published posts to everyone but the owner).
- Private messages are not covered by posting restrictions.
- Not built: moderator report assignment, appeal evidence uploads, email/push alerts for moderation notices, appeals by moderators about their own revoked access.
